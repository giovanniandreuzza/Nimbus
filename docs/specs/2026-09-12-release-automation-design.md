# Release automation — design

Date: 2026-09-12
Status: proposed
Target: infrastructure only; no library code changes

## Problem

Nimbus is published to Maven Central with a GPG-signed, multi-target artifact set, and every
step of getting it there is manual and unrecorded.

- **No CI.** `.github/` does not exist. Nothing builds a pull request. The last full
  `./gradlew build` across all targets is not known to have run.
- **No tags.** `git tag -l` is empty for a library with seventeen published versions. There is
  no commit in this repository identifying what 2.2.0 was built from.
- **`CHANGELOG.md` has been empty since January 2025**, while the README links to it as "a
  summary of changes in each release".
- **The version lives in a file nobody bumps on purpose.** `versions.properties` was at 2.1.0 in
  the last commit while 2.2.0 was published from an uncommitted local edit. `README.md` still
  advertises 2.1.1.

The README staleness is worth a second look, because the mechanism to prevent it already exists
and failed anyway. `README.md` is generated from `README.md.template` by a `generateReadme` task
wired into `tasks.build`, substituting `$VERSION` from `versions.properties`. It is stale because
the bump and the regeneration are two separate manual acts, and only one of them happened. A
second source of truth that has to be kept in sync by hand is not a safeguard; it is one more
thing to forget.

## Why now

2.3.0 is finished and unreleased. Fifteen conventional commits across content digest, the core
storage port, five transport fixes, tests on every target, and the sample app are sitting on a
local branch with no remote, no CI, and no path to Central that isn't a person typing Gradle
commands with a GPG key in reach. The release process should exist before it carries that.

## Design criteria

1. **Nothing reaches Maven Central without a human seeing exactly what it is.** A version on
   Central is permanent: it cannot be deleted or overwritten. The gate matters more than the
   convenience.
2. **One source of truth per fact.** The version is in one file. The changelog is derived from
   commits. Nothing is kept in sync by hand.
3. **Enforcement that works on this account's plan**, not enforcement that works in the docs.
4. **Recoverable.** Every failure mode has a written procedure, because the failures happen
   months apart and nobody remembers.

## Decisions

### release-please, not a hand-rolled bump script

release-please computes the version from conventional commits, writes the changelog, and opens a
pull request proposing the release. Merging that pull request is what tags and releases.

The alternative considered was a ~60-line shell script computing the bump and pushing to `main`
directly. It was rejected once `main` became protected: a design whose central act is an
unreviewed push to a protected branch is fighting the protection rather than using it. The
review gate is the point — the release pull request shows the exact version and the exact
changelog before anything irreversible happens.

Cost of the choice, stated plainly: release-please tags and creates the GitHub Release *before*
the artifacts are published, so a failed publish leaves a tag with nothing behind it. See
**Failure modes**.

### `version.txt`, not `versions.properties`

`simple` is release-please's release type for a project it has no native support for — and there
is no Kotlin or Gradle strategy: the strategies that ship cover Node, Java/Maven, Python, Rust
and friends, none of which describes this build. `simple` updates `version.txt` with its default
updater.

Using that default file removes a moving part. `versions.properties` would have needed
`x-release-please-start-version` / `x-release-please-end` marker comments and an `extra-files`
entry with the `generic` updater; `version.txt` needs neither. Both Gradle modules read it
directly:

```kotlin
version = rootProject.file("version.txt").readText().trim()
```

replacing ten lines of `Properties` loading per module. `versions.properties` is deleted.

### README generated by release-please, not by Gradle

`README.md.template`, the `generateReadme` task and the `tasks.build.dependsOn("generateReadme")`
wiring are all removed. `README.md` becomes an ordinary tracked file whose dependency snippet is
wrapped in release-please markers:

````markdown
<!-- x-release-please-start-version -->
```kotlin
dependencies {
    implementation("io.github.giovanniandreuzza:nimbus:2.2.0")
    implementation("io.github.giovanniandreuzza:nimbus-ktor:2.2.0")
}
```
<!-- x-release-please-end -->
````

This is the one place the version appears twice, and release-please updates both in the same
commit, so they cannot drift.

Keeping the template was considered and rejected: the 2.3.0 branch edits `README.md` directly,
which the next `./gradlew build` on `main` would silently overwrite. The template is a trap for
exactly the edit a contributor would naturally make.

### A GitHub App token, not `GITHUB_TOKEN`

This is forced, not preferred. The release-please action documents it: *"events triggered by the
`GITHUB_TOKEN` will not create a new workflow run."* With a required status check on `main`, a
release pull request opened under `GITHUB_TOKEN` would never run CI, would never report the
check, and could never be merged. The automation would deadlock on its own first release.

A GitHub App (`actions/create-github-app-token`) is used rather than a personal access token
because fine-grained PATs expire — at most a year — and the failure lands months later as an
opaque permissions error on a release nobody can ship. The App's installation token is minted per
run and scoped to this repository alone.

### The conventions gate runs from the base branch

For a `pull_request` event GitHub evaluates the workflow, and any script it calls, from the
**merge ref** — head merged into base. A pull request can therefore rewrite `ci.yml` or
`check-conventions.sh`, keep the job names, and turn its own required checks into no-ops. With a
zero-approval ruleset that would leave the maintainer's eyes as the only gate.

So the conventions check runs on `pull_request_target`, which takes the workflow from the base
branch. It never touches pull request content: it checks out the base, and reads commit subjects
through the API rather than fetching or executing anything from the head. That removes the usual
`pull_request_target` hazard, which is checking out head code with a privileged token.

`build` stays on `pull_request` and stays rewritable, because it inherently executes pull request
code and no configuration changes that. Its job is to answer "does this compile", not to be a
security boundary. It is a required check because a red build should block a merge, not because
a green one proves anything about a hostile pull request.

Consequence to plan around: a `pull_request_target` workflow only runs once it is on the base
branch, so the gate does not run on the pull request that introduces it.

### Conventions enforced in CI, not in the ruleset

GitHub's list of available ruleset rules covers creations, updates, deletions, linear history,
pull requests, status checks, force pushes and file path/size restrictions. It does not list
metadata restrictions — commit message pattern, branch name pattern — for this repository type,
and this is a personal account rather than an organisation. Rather than design around a rule that
may not be grantable, conventions are enforced as a required status check: a shell step with the
allowed types written out in the workflow. It works on any plan, the rule is readable in the
file that enforces it, and the error message says what was wrong.

If metadata restrictions turn out to be available, they can be layered on later as defence in
depth. They are not the mechanism this depends on.

### Rebase merges for multi-commit branches

Squash-only was the first recommendation and is wrong for this repository. The changelog is
generated from the commits that land on `main`; squashing fifteen carefully written conventional
commits produces a 2.3.0 changelog with one line in it, and makes enforcing conventional commit
messages pointless, since only the pull request title would survive.

Merge settings: **squash and rebase enabled, merge commits disabled.** A single-commit pull
request squashes; a multi-commit one rebases and every commit reaches `main` as written. Both
produce linear history, so the ruleset's linear-history rule holds either way.

## Components

### Configuration

**`release-please-config.json`**

```json
{
  "bootstrap-sha": "acb87a1daa84a39d80e8d1e1fed198fb6a584af7",
  "packages": {
    ".": {
      "release-type": "simple",
      "package-name": "nimbus",
      "include-v-in-tag": true,
      "extra-files": [{ "type": "generic", "path": "README.md" }],
      "changelog-sections": [
        { "type": "feat",     "section": "Features" },
        { "type": "fix",      "section": "Bug Fixes" },
        { "type": "perf",     "section": "Performance" },
        { "type": "refactor", "section": "Internal" },
        { "type": "docs",     "section": "Documentation" },
        { "type": "test",  "hidden": true },
        { "type": "build", "hidden": true },
        { "type": "ci",    "hidden": true },
        { "type": "chore", "hidden": true }
      ]
    }
  }
}
```

`bootstrap-sha` is the current tip of `main`. Without it, the first run parses commits back to
2025 and generates a changelog for seventeen historical releases. It is ignored once the first
release pull request merges and can be deleted then.

**`.release-please-manifest.json`** — `{ ".": "2.2.0" }`. This is what tells release-please the
current version in the absence of tags.

**No `package-name`.** Naming the package makes release-please treat the root as a named
component: it appends `--components--nimbus` to its branch name and prefixes the tags
(`nimbus-v2.3.0` rather than `v2.3.0`). This was learned by shipping it — the first run produced
exactly that. The repository publishes two artifacts from one version, so it has no components,
and the branch name matters beyond cosmetics: the conventions check has to recognise it, or the
release pull request cannot pass its own required check.

**`version.txt`** — `2.2.0`. Written by release-please from here on; never edited by hand.

### `conventions.yml` — on `pull_request_target`

One job, `conventions` (ubuntu), running the base branch's copy of
`.github/scripts/check-conventions.sh` and validating, against a single list of allowed types
defined at the top of that script:

- the branch name, against the Conventional Branch vocabulary: `main`, `develop`, and `feature/`,
  `bugfix/`, `hotfix/`, `release/`, `chore/` followed by lowercase alphanumeric segments separated
  by single `-`, `_` or `.`; branches beginning `release-please--` are allowed as a family, since
  the bot's own branches cannot satisfy a convention that forbids consecutive hyphens and their
  exact name depends on its configuration
- every non-merge commit in the pull request, as `type(optional-scope)!: subject`
- the pull request title, in the same form — it becomes the commit message when squashing

The script reads subjects from stdin rather than calling git itself, so the caller chooses the
source. This workflow supplies them from `gh api .../pulls/N/commits`, filtered to commits with
fewer than two parents — no fetch of head, nothing from the pull request on disk.

Merge commits are excluded deliberately: only squash and rebase merges are allowed into `main`,
and neither puts a merge commit there, so validating one would fail a branch that merged `main`
into itself over a commit that will never exist on `main`.

### `ci.yml` — on `pull_request`

One job, `build` (macos-latest): JDK 17 Temurin, `gradle/actions/setup-gradle` for caching,
`./gradlew build` — every target, every test, sample app included. macOS because the iOS targets
do not compile anywhere else; the repository is public, so macOS minutes are free. Test reports
uploaded as an artifact on failure.

`conventions` and `build` are both required status checks.

### `release.yml` — on `push` to `main`

`permissions: contents: write, pull-requests: write, issues: write`.

Permissions are per job rather than workflow-wide, so the publish job does not hold write access
while the signing and Maven Central secrets are in scope.

- **`release-please`** (ubuntu, `contents`/`pull-requests`/`issues: write`): mints an App token via `actions/create-github-app-token`, then
  runs `googleapis/release-please-action@v4` with it. Outputs `release_created` and `tag_name`.
- **`publish`** (macos-latest, `contents: read`, `needs: release-please`, `if: release_created`): checks out
  `tag_name`, then `./gradlew publishAndReleaseToMavenCentral` — the task that uploads *and*
  releases, so no manual click in the Central Portal. Credentials arrive as environment
  variables: `ORG_GRADLE_PROJECT_mavenCentralUsername`, `…Password`, `…signingInMemoryKey`,
  `…signingInMemoryKeyPassword`. No `…signingInMemoryKeyId`: Gradle wants the short
  eight-character form and rejects the long one — which failed the first publish — and the
  exported keyring holds a single secret key, so the id is optional. The input was removed rather
  than corrected.

Publishing is gated on the `release_created` output inside the same workflow rather than
triggered by `on: release`, so it does not depend on which token generated the release event.

Signing in CI uses the in-memory key. The local setup signs with
`signing.secretKeyRingFile`, a keyring on disk, which has no equivalent on a runner.

### Ruleset on `main`

Created through the API, targeting `refs/heads/main`:

- pull request required, **zero required approvals** — a solo maintainer cannot approve their own
  pull request, so requiring one approval would lock the only maintainer out of their own
  repository, the bot's release pull request included
- required status checks: `conventions`, `build`
- force pushes blocked, deletion blocked, linear history required
- squash and rebase as the only allowed merge methods, enforced by the rule itself
- **no bypass actors.** The REST documentation for bypass actors lists the valid `actor_type`
  values but not the numeric `actor_id` for each repository role, and on a public repository a
  wrong id grants bypass to everyone with read access — that is, to everyone. A self-bypass would
  also mean the protection does not apply to the only person able to breach it. The escape hatch
  is disabling the ruleset in Settings, which is deliberate friction and leaves a trace.

Plus repository settings: squash and rebase merges only, squash commit message taken from the
pull request title, branches deleted on merge.

## The resulting flow

```
branch feature/… → pull request → conventions + build green → rebase onto main
   → release-please opens or updates "chore(main): release X.Y.Z"
        (CHANGELOG.md, version.txt and README.md already written in it)
   → CI runs on that pull request too — this is why the App token is required
   → a human merges it when they decide to ship
        → tag vX.Y.Z + GitHub Release + publish to Maven Central
```

Two gates: the feature pull request, and the release pull request.

## Failure modes

**Publish fails after the release exists.** The tag and GitHub Release are created when the
release pull request merges; publishing happens after. A failure in between leaves a tag with no
artifacts. Re-run the `publish` job — it is idempotent as long as the version is not already on
Central. The risk is small because CI has already built that exact commit on the release pull
request, which leaves credential and Central-side failures as the realistic causes.

**The version is already on Central.** Nothing on Central can be deleted or overwritten. Recovery
is to release the next patch version; do not attempt to re-publish.

**The release pull request shows a version you did not expect.** Do not merge it. The cause is
almost always a commit type: `feat!:` or a `BREAKING CHANGE:` footer produces a major bump. Fix
the commit history on the offending branch; release-please recomputes when `main` changes.

**A release pull request appears for changes not worth releasing.** Expected, and not a defect.
Observed on the very first run: two `docs:` commits produced a proposed 2.2.1. release-please
opens a release pull request for any conventional commit since the last release, not only for
`feat` and `fix`. Leave it open — it is recomputed and rewritten on every push to `main`, so it
rolls forward into the next real version rather than accumulating. The gate is that a human merges
it, and merging is what releases; an open release pull request has released nothing.

**A release pull request was merged by mistake.** `last-release-sha` in the config overrides where
release-please starts gathering commits, and unlike `bootstrap-sha` it is never ignored.

## Rollout order

There is a circular dependency: the ruleset cannot require a status check named `build` before
`ci.yml` exists on `main`, and once the ruleset exists nothing reaches `main` without passing it.

1. **Pull request 1 — the automation itself**, merged before protection is enabled: workflows,
   release-please config and manifest, `version.txt`, both `build.gradle.kts` files switched to
   read it, `versions.properties` deleted, README de-templated with markers, `CHANGELOG.md`
   seeded with a header noting that pre-2.3.0 history lives in git. Every commit here is
   `ci:`, `build:`, `docs:` or `chore:` — none releasable, so release-please proposes nothing.
2. **Verify CI runs green once**, which is also what makes the check names exist.
3. **Manual, by the maintainer**: create and install the GitHub App, add all seven secrets.
4. **Create the ruleset and merge settings.**
5. **Pull request 2 — 2.3.0**, rebase-merged. release-please then proposes 2.3.0.

## What pull request 1 must not commit

`main`'s working tree is dirty, and all of it is already in the 2.3.0 branch — in better form.
This was verified rather than assumed: every modified tracked file is byte-identical to
`e6c64ff`, the branch's `chore: import uncommitted working state as 2.3.0 baseline`. Stash it;
do not delete it and do not commit it.

Three traps, each of which would create a conflict against the 2.3.0 branch:

- **`docs/specs/2026-09-11-content-digest-design.md` and `…-storage-port-layering.md`** are
  untracked here *and* added by the branch, with different content — the branch revised them to
  match what shipped. Pull request 1 commits only this design document; those two arrive with
  2.3.0.
- **`nimbus/src/jvmTest/`** is untracked here and superseded by the branch, which moved
  `DownloadStoreSchemaTest`, `DownloadStoreRecoveryTest` and `DownloadStoreVersionTest` into
  `commonTest` so they run on every target. Do not commit the `jvmTest` copies.
- **`.claude/` and `graphify-out/`** are local tooling output. They belong in `.gitignore`,
  which pull request 1 adds.

Pull request 1 therefore touches only: the two workflows, `release-please-config.json`,
`.release-please-manifest.json`, `version.txt`, both `build.gradle.kts` files, the deletion of
`versions.properties` and `README.md.template`, `README.md`, `CHANGELOG.md`, `.gitignore`, and
this document.

## Landing 2.3.0

The work is on `worktree-nimbus-2-3-0-tests`, fifteen commits ahead of `main`, local only, no
remote branch — so it can be rewritten freely. Three things must be fixed before it becomes a
pull request:

- **Two commits use `sample:` as their type**, which is not a conventional commit type and would
  fail the `conventions` check. `sample` is a scope, not a type: reword to `feat(sample):` and
  `chore(sample):`.
- **The branch bumps `versions.properties` to 2.3.0.** Under release-please the version file is
  written by the bot. Drop that change; the file itself is deleted by pull request 1.
- **The branch edits `README.md` directly** while `main` still generates it from the template.
  After pull request 1 removes the template this is correct as written, but the two changes touch
  the same file and the rebase has to be done in that order.

Both pull requests edit `nimbus/build.gradle.kts` — pull request 1 changes how the version is
read and removes `generateReadme`, the branch adds test dependencies — so the rebase conflicts
there. It is a small, mechanical conflict, but it is expected rather than a sign something is
wrong.

The branch name itself does not satisfy the convention. It lands as `feature/`-prefixed.

## Validating the automation

Workflows cannot be unit tested, so validation is staged deliberately:

- `./gradlew build` run locally on macOS before pull request 1, so a CI failure means the
  workflow is wrong rather than the build.
- The `conventions` regexes are a shell script and are exercised against a fixture list of good
  and bad branch names, commit subjects and pull request titles — including
  `release-please--branches--main` and `release-please--branches--main--components--nimbus`, both
  of which must pass, and `sample: something`, which must fail.
- Pull request 1 is itself the first live run of `ci.yml`.
- The first release is 2.3.0, with a maintainer reading the proposed changelog before merging.

## Open questions

- **Whether `dev` survives.** The repository's history is `dev` → pull request → `main`. With
  short-lived `feature/` branches and a ruleset on `main`, `dev` is a third place for work to sit
  and get stale. It is left in place here because deleting it is a workflow change, not a release
  automation change. Decide separately.
- **Whether the `publish` job should verify the artifact after upload** — resolving the published
  coordinates from Central before declaring success. It would catch a silent partial upload. Not
  in this design because Central's indexing delay makes the check flaky, and the failure it
  guards against has not been observed.
